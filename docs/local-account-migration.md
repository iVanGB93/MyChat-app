# Local-account migration

Status: opt-in development milestone; the legacy app remains the default entry.

Current implementation and validation are recorded in the dated sections below; earlier milestone descriptions are historical. New accounts use twelve recovery words and signed word-only recovery discovery. Core message actions, hosted own-media receiving/forwarding/uploads, and FirstNeuron's own voice/video call interface with signed relay and wake delivery are now implemented. Basic groups are now implemented and tested across two emulators and FirstNeuron. Remaining work includes group feature parity, cold internet discovery with multiple reachable bootstrap neurons, physical biometric/background/separate-network checks, default-entry cutover and the final local APK.

## Current release decision: fresh accounts

On October 4, 2026 the user explicitly chose a fresh start for everyone and accepted losing previous account information and chats. This supersedes the legacy-account/history import requirements below. Do not spend release work on preserving old numeric-user accounts, chat rooms, contacts, identity pins or blocks.

The new onboarding offers creation of a fresh cryptographic identity, protected by a local password, confirmed recovery words and optional biometric unlock. Restore is only for an existing new-system identity and its recovery record; it does not restore Django accounts. Contacts exchange their new public identity codes. Existing local test identities are not automatically wiped on every launch.

The active local-account UI and network no longer import the legacy migration adapter or message database. Old migration helpers remain inactive development code, not a release dependency. No device data was erased to implement this policy. A dependency-boundary regression test guards the new entry against accidentally importing legacy authentication/history adapters.

Remaining release gates are tracked in the current status above and dated validation notes below. Switch the default entry only after those checks. Build the APK locally when ready, as requested; no APK has been built for this milestone.

## Implemented

- index.ts selects LocalAccountApp only when EXPO_PUBLIC_AXONIC_LOCAL_ACCOUNT=1. Otherwise it loads the unchanged legacyEntry.ts. The local branch does not initialize AuthProvider, Axion, legacy push handlers, or legacy telemetry bootstrap.
- A separate local-account vault uses the existing native secure randomness and scrypt implementation, XChaCha20-Poly1305 encryption, and a device secret in SecureStore. Existing Django accounts, migration identities, and message databases are not replaced.
- Creation requires re-entering the 24 recovery words before saving. A local display name is a device label, not a globally registered username. Passwords are 12–256 characters and never sent to peers.
- Optional biometric unlock stores the unlock credential using SecureStore requireAuthentication, a separate keychain service, and WHEN_UNLOCKED_THIS_DEVICE_ONLY. Enrollment first verifies the local password. Cancelled/ineligible/invalidated biometric credentials preserve password fallback. Deletion removes only the biometric credential, not the vault.
- Backgrounding locks the identity, closes its axons, invalidates pending biometric operations, and clears sensitive form state. iOS inactive transitions hide the form without treating the biometric prompt itself as cancellation. Cold starts require unlocking.
- Once unlocked, the app participates through LAN discovery and the pinned FirstNeuron bootstrap using signed root identity proofs. It shares the 3–10 axon limit, default 5, and bounded encrypted custody service. This composition now includes authenticated RTC discovery across introduced internet peers; live verification of the new local-account chat composition is pending.
- Public identity and signed recovery metadata can be shared. Recovery creates a replacement device under the same root, retains bounded signed ancestry, and requires an explicit unlock afterward.

## Recovery constraints

Recovery currently requires BOTH the private words and the latest signed public recovery record. A copied record is not a globally fresh authority: restoring from an old record can fork/conflict with peers holding a newer revision. The UI explicitly warns about this; it never creates a new genesis identity from the same words.

Recovery replaces all devices authorized in the supplied record. It does not link another device, restore old message history, or recover ciphertext encrypted to previous device keys. Public records renew over time, so saved metadata must be refreshed. Automatic authenticated record discovery and a conflict/revocation strategy are required before making recovery a production onboarding flow.

## Development use

Keep the flag absent for normal app testing and EAS builds. Do not reuse a normal user's recovery words for testing.

### Transfer controls and finished-job retirement (October 4, 2026)

The label deliberately describes a local pause: chunks already sent to another neuron can still arrive. Pausing revokes in-flight work and preserves the checkpoint; resuming keeps incoming progress and safely re-offers outgoing uploads. The UI explains this scope. Expired transfers cannot resume, blocked contacts cannot retry, and a verified recipient receipt cannot be cancelled while cleanup is pending.

Confirmation of two sampled words is a backup usability check, not an authentication or recovery mechanism. Recovery requires the complete valid phrase plus its matching root-signed record, replaces device keys, and preserves the root account. The UI sends only the derived public account during discovery, then checks the signed record twice before committing recovery. Reachable peers cannot prove that no newer record exists elsewhere; unavailable/conflicting history prevents this recovery path. Recovery does not restore lost local chats.

The vault uses XChaCha20-Poly1305, fresh salt/nonce and associated data binding its version, fixed KDF/cipher identifiers and current signed record digest. Unlock requires both the local password and OS-protected device secret. The native adapter implements scrypt N=131072, r=8, p=1, dkLen=32; live execution of the installed emulator native module matched independent OpenSSL outputs for ASCII, Spanish/emoji and unpaired-surrogate fixtures. Unit tests exercise real portable scrypt and independent Node/OpenSSL derivation; lightweight controller fixtures use a test KDF only to exercise state transitions. The Android merged manifest references SecureStore backup exclusions for cloud backup and device transfer.

Confirmed issues and fixes:

- A delayed startup policy read could overwrite newly enabled automatic locking and resume the cached credential. Startup now captures its cancellation epoch before the first read and rejects superseded work.
- Enabling locking deleted the cached credential before persisting the policy; a deletion failure left automatic startup login possible. The lock preference is persisted first, and credential cleanup is attempted even if the preference write fails. A persisted lock preference denies automatic login even if optional cleanup is temporarily unavailable.
- An invalid lock preference was treated as an opt-out. Only an absent preference or explicit 0 permits ordinary automatic resume; malformed values require explicit login. The separately recognized locked marker represents manual locking, not an automatic-lock opt-in.
- Manual locking had no durable denial if credential deletion failed. Manual lock now persists a locked marker before attempting deletion. Restart requires explicit authentication while keeping automatic locking off. A successfully authenticated remembered login clears this marker. Queue ordering and epochs prevent late writes from surviving a subsequent lock.

Default remembered login remains intentionally enabled at the user's request and uses device-bound OS SecureStore, not public profile/AsyncStorage credential storage. This review does not claim protection against a compromised/rooted operating system, memory inspection, or rollback of all local/OS storage. Mutable byte buffers are wiped where owned; JavaScript/Kotlin strings and platform intermediates cannot be claimed securely erased. Real-phone biometric behavior and camera/background checks remain hardware validation work.
