Actual encrypted chunk-size experiment — 2026-10-18

Purpose and scope
Compare 4, 16, 64 and 256 KiB actual independently encrypted/proved chunks,
not merely different batch counts. Shipping protocol/chunk sizes are unchanged.
The native SHA-256 helper's bounded local input limit was extended separately
to make the second experiment use the same acceleration at every size.
Other existing dirty changes predate this experiment.
Only a separately loaded experimental codec and synthetic cache files run in
the main unlocked Axonic Dev debugger. No AoN updates, normal-app access,
official-app installations, history changes, queue resets, commits or pushes.

Source correspondence and compatibility
scripts/experiments/attachment-chunk-sizes.cjs derives the codec from the
current attachmentProtocol.ts by changing the chunk constant in an isolated
module and domain-separating EVERY attachment authentication/hash domain by
the experimental size. The normal module remains loaded and unchanged.
Actual XChaCha20-Poly1305, Merkle proof checks, manifest signatures and signed
receipts execute, including final file size/SHA-256 before receipt creation.
Independent PC receipt validation follows. This is NOT a deployable new
protocol version: size is fixed out of band by the isolated experiment.
Legacy signature verification rejects these experimental manifests.
Production rollout would need explicit version/capability negotiation, native
preparation/verification support, journal/file offsets and transport framing
compatibility. A successful test does not establish cryptographic security.

Execution and measurement contract
Runner: node scripts/benchmark-dev-chunk-sizes.cjs [--smoke]
Phone: com.axonic.dev on SM-S948U1, foreground Hermes/Metro development build.
PC endpoint: temporary loopback-only WebSocket, random per-run path, reached
through an ADB reverse mapping installed and removed by this runner.
Only synthetic encrypted files cross it. This is actual transfer to Dev, but
NOT an AoN/Internet test and NOT the production authenticated scheduler,
custody, retry, chat-publication or notification workflow.

Transport payload budget stays 256 KiB across sizes. One response is consumed
at a time; no artificial latency. Receiver writes in <=128 KiB pieces so
larger cryptographic chunks do not also win by reducing disk writes.
Receiver yields after processing >=64 KiB (one 256 KiB chunk cannot yield
inside its synchronous cryptographic call). The original native helper was
bounded to 4 KiB chunks, so first compare all four candidates using the same JS
leaf hash, plus a separate 4 KiB native-leaf reference. Do not attribute the
accelerator difference to chunk size.

Memory observations
sampledHeapBytes is the largest sampled Hermes js_heapSize for the whole Dev
runtime during the test, not isolated allocation or process peak RSS. It can
include earlier app/debugger/GC state. Ciphertext hex/base64 and proof objects
add allocations beyond plaintext buffers. No total-memory bound is claimed.
Keys belong only to fresh synthetic identities/files. Owned byte arrays are
wiped where practical; immutable strings/engine internals are not claimed
to be securely erased. The normal account's keys are never read.

Thermal/host-load qualification
Android was awake with Dev resumed; early thermal status was 0. Later in the
native large series status was 2. The current synthetic operation was
explicitly cancelled, retaining its partial cache file and recording the
cancellation as a failure rather than silently excluding it. Six native
large-file observations had already completed. No functional integrity
failure occurred in those completed transfers.
The remaining two repetitions were restarted in a separate continuation with
a pre-run thermal guard (status must be 0, bounded cooldown wait), and both
before/after thermal values recorded. Never pool these as an unqualified
controlled speedup estimate. Initial all-JS exploratory repeats also overlap
some PC build/test work; that round is not the headline performance comparison.

Decision
Do not change the shipping 4 KiB format based on this experiment. Larger
chunks cut metadata but did not establish a repeatable encompassing speed
gain here. 64 KiB had the fastest single cooled observation, not a consistent
win. 16 KiB is a conservative candidate for a future compatible prototype
because it captures most response-size savings with shorter atomic work;
it is NOT an experimentally proven faster production default. 256 KiB adds
long uninterruptible processing for little extra response-size reduction.
The next useful target is per-byte conversion and verification/decryption on
the JS thread, with native/background execution preserving proof/AEAD checks,
durable writes, cancellation and final receipt semantics. Moving that work
may change the best chunk size; this remains a hypothesis requiring tests.
Any production format must additionally negotiate size/version and respect
RTC fragmentation/frame limits, old jobs, native preparation, relays and
both app/AoN compatibility. No new format was enabled and no AoN changed.

Production-readiness cleanup (same date)
The temporary 524448-byte native hash-input allowance used above was removed.
Shipping AttachmentHash accepts the existing bounded 8300-byte canonical input.
The experimental codec remains isolated in scripts/tests, not in app imports.
Historical native-all measurements describe the explicitly widened experimental
binary, NOT the final readiness APK. Its runner's capability check rejects the
shipping binary before running larger native-leaf experiments.
