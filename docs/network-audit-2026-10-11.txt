Priorities / evidence / proposed work

1. HIGH: background delivery needs a dedicated acceptance gate.
Evidence: fresh backgrounded Dev receiver resumed attachment on foreground.
rootPushRegistration.ts always requests FIRST_NEURON.account; push token
registration is not distributed across arbitrary connected neurons. This is an
explicit transitional dependency, even though custody can use other peers.
The audit did not establish whether an FCM wake was sent/received for this test.
Next: correlate one test's deposit, signed wake, gateway acceptance, Android
receipt, recovery and visible notification with timestamps. Test screen-off and
process-restart separately. Keep content arrival distinct from notification.
Do not claim AoN gateway ACK proves phone delivery or silently change gateways.

2. HIGH: attachment preparation can starve ready transfer work (source finding).
rootAttachmentRuntime.ts tick processes a selected outgoing item before the loop
that enqueues incoming messages and before worker.tick. Missing peer record
awaits lookup then returns; preparation success/error also returns. An unresolved
selection can repeat indefinitely, and a batch of preparations delays existing
transfers. This control-flow risk is separate from the background trial and has
NOT been established as the cause of that trial.
Next: independent bounded preparation and transfer scheduling; single-flight
lookup with backoff. Regression: one unresolved outbound selection must not stop
an unrelated valid incoming file, cancellation or receipt handling.

3. HIGH: RTC transfer waits are the main measured speed opportunity.
Current RTC frames remain20KB; small batches carry3x4KiB chunks, two batches in
flight (24KiB payload window). Worker waits for the entire window to settle,
verifies/writes/checkpoints it, then requests the next window. Prior device timing
shows network waits dominate file reads/writes and signature lookup work.
Increasing to four batches did not establish improvement; advertisement remains
disabled. Do not re-enable by default from unit results alone.
Next: bounded sliding receive window with ordered commits and backpressure;
control-frame reserve; preserve cancellation, replay bounds, integrity checks,
legacy negotiation and fairness. Measure matched same-route trials and p50/p95.

4. MEDIUM: transport capacity differs from the user-visible axon limit.
rtcAxonTransport.ts make() rejects at entries.size>=5. Mobile pool allows up to10.
Thus ten allowed axons does not mean ten simultaneous RTC peer channels; mixed
LAN/AoN links can still fill the pool. A cap is sensible but should be explicit
or derived from a separate resource budget. Do not blindly raise it: memory,
concurrent handshakes and battery need measurement. No >5-real-peer load test here.

5. MEDIUM: LAN compatibility and route recovery need broader hardware coverage.
AxonLan.kt requires Android API33+ and a private IPv4 Wi-Fi address. It binds NSD
and local listener to Wi-Fi, without requiring validated internet. Guest isolation,
blocked multicast and IPv6-only networks are not covered by this path.
lanIdentityRuntime.ts defers failed LAN peers120s, while foreground resume clears
that deferral. This protects against stale discovery loops but can temporarily
retain a slower route after a transient failure. Measure recovery before tuning.
The two-brand-new-identities/no-internet scenario was NOT run in this audit.

6. MEDIUM: repeated polling and full-history work grow with history/peer count.
Runtime ticks once/sec; custody polls each connected relay every5s (bounded four
packets/pass); discovery/renewal share control exchanges. Attachment pump idle
poll is200ms and reads ledger/queued selections; active steps scan pending messages.
This is bounded by connection limits but not a demonstration of large-history
performance. Next: change notifications/revision-indexed pending work, adaptive
idle polling and runtime counters for request latency, queue age and retries.
Do not interpret 815 passing tests as thousands-of-users load validation.

Confirmed safeguards retained
- Account lock/lifecycle invalidates active sessions and work; aborts reserve
  pending connection capacity until cleanup finishes.
- Signed authentication and expiry enforced; discovery grace bounded15s and
  capped at peer expiry; initial handshake remains bounded.
- LAN route upgrades keep working connection until replacement authenticates.
- Retry backoff, request/frame/queue limits, identity checks and checksum/receipt
  verification remain present.
- Custody acceptance is distinct from delivered/read; retries preserve durable
  checkpoints and receipts; no cloud upload was mistaken for delivery.

Recommended implementation order
A. Prove and fix preparation/transfer scheduling isolation with a regression test.
B. Background wake/recovery acceptance tests using Dev, with end-to-end evidence.
C. Sliding RTC media window with measured backpressure, then matched device trials.
D. Capacity/polling scalability and disconnected-LAN/new-identity hardware matrix.
