These are ten responsibility areas, NOT ten newly extracted packages. Existing
public facades live in src/modules; many implementations remain under
src/services/identity. That folder name does not make every file identity code.
Each guide separates today's entry points from the next extraction opportunity.
The first implemented separation is storage roles and connection/transfer ports:
both phone and AoN transfer composition now use the same grouped dependencies.
See storage.txt and transfers.txt for the contracts and their regression checks.
Attachment connection selection is also shared and separated from retry scheduling
and durable transfer progress; its policy and limits are described in transfers.txt.

Dependency direction (target contract)
  UI or AI adapter -> application commands -> domain rules and storage ports
  composition -> connects commands, network, transfer, storage and diagnostics
  network -> authenticated peer sessions; transport -> moves bytes on sessions
  custody -> durable encrypted relay work; messaging -> own message semantics
  platform adapters -> native/Node APIs behind injected ports
  presentation state <- published observations; never authority for permissions

Existing cross-area imports are documented; this diagram is not a claim that all
layers are already mechanically isolated. Do not create one all-powerful manager.
Shared utilities (change signals, deadlines, read-ahead) are mechanisms, not new
owners of message state. Domain owners decide policy; composition owns lifetime.

Typical paths
  Send text: UI/AI command -> ledger commit -> delivery scheduler -> direct peer
    or encrypted custody -> verified recipient receipt -> ledger -> UI/events.
  Receive: authenticated transport -> protocol validation -> own durable inbox
    or relay custody (different stores) -> receipt only after required commit.
  Media: select/reference file -> descriptor/job -> direct stream if eligible,
    otherwise encrypted v4 relay blocks -> verified file -> signed receipt.
  Wake: verified hint -> bounded runtime lease -> shared recovery pump -> receipt
    and drain evidence or deadline -> release lease; hint alone is not delivery.

Repository roles
  Axonic-app: canonical shared TS services, mobile composition/UI/native adapters.
  Axonic-neuron: hosted composition/storage/dashboard/AI adapters and generated
    shared copies. Current integration worktree is locally under mobile builds/
    aon-operator-20261022; do not hard-code that temporary layout into runtime.
  Axonic (Django): website/update/legacy routes; not the current phone composition
    root. Do not delete routes merely because the new phone entry bypasses them.

Working procedure
  1. Check git status in the actual checkout; preserve unrelated work.
  2. Read one module guide. Identify state authority and cancellation owner.
  3. Change canonical logic once; use adapters for platform differences.
  4. Run module regressions, boundary checks and shared parity when relevant.
  5. Update that guide if a contract/entry point changed. Put measured incident
     evidence in dated reports, not duplicated across every module guide.
  6. State local/tested/deployed separately. No guide authorizes release or wipes.

Public API organization (October 25 follow-up)
  Calls and media no longer travel through the messaging barrel. All consumers
  use the owning facade; no duplicate implementations or compatibility barrels.
  All screens/components/navigation TS/TSX now participate in boundary checks.
  Native keyboard layout is behind the UI adapter. Relay inventory presentation
  is exposed through the network facade, without UI imports of protocol services.
