Trial credits v1 — 2026-10-31

Purpose
Separate persistent experimental accounting from the session contribution scorecard and current health. No service restriction, balance gate, cash value, transfers, offline penalty, or synchronized multi-device balance. Negative balances are allowed. The policy is provisional, not a reward economy or consensus system.

Policy
100 credits once per local identity ledger. +1 for each unique verified relay recipient receipt (private/group message); media completion earns a separate +1. -1 simulated spending per sender message/recipient whose relay custody is confirmed. Direct delivery is not charged. No credit for storage alone, retries, polls or errors. Reference = SHA256(sender, message id, recipient); event kind distinguishes message/media completion and use. Re-encryption and duplicate acknowledgments do not change that reference.

Architecture
Shared services/identity/trialCredits.ts owns policy, validation and idempotency. Existing custody receipt callbacks fire after successful durable custody transactions; existing courier-held callbacks record simulated usage. Phone mobileTrialCredits uses its own indexed SQLite table scoped by owner. Hosted adapter reuses indexedStore; database name is scoped to canonical neuron account. Append-only observation rows and a materialized balance update atomically in one transaction. UI consumes an observed global state; hosted dashboard refresh uses existing change events. No new periodic task or history scan.

Failure semantics
Credits never hold up delivery. Accounting errors mark the balance unavailable; corrupt state is not cleared or granted another allowance. Relay commits and credit commits are separate: a crash or failed accounting write can omit an observation until a duplicate receipt/held callback arrives. There is no automatic backfill or durable cross-ledger settlement. These limitations, local integrity and possible peer collusion must be addressed before assigning real value or enforcing a balance.
