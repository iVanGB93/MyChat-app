TURN evidence and limitation
- Original test changed ICE config after borrowing an established direct peer. Immutable bundle configuration and reused ICE state made the test misleading. Relay candidates alone did not prove selected relay routing.
- Initial diagnostic substituted fresh leases to isolate TURN infrastructure. The final scripts/test-dev-turn-call.cjs instead only makes shared acquisition fail and sets the existing ICE provider policy to relay: production callPeerSelection creates and cleans up the connection. It requires actual selected relay/relay and received video. The signed custom SDP marker is validated in application signaling; native SDP normalization can remove it, so the harness does not inspect the native copy for that marker.
- Real two-way video selected relay/relay. User confirmed moving screen share and camera return. Counters captured screen frames at receiver, then both camera senders restored. Sustained run had zero freezes; small packet loss (10/15 reported packets) was present, so this is not a zero-loss claim. Reverse-originating TURN call also passed and ended cleanly.
- This gap was subsequently fixed locally: callPeerSelection allows a 1.5-second shared-acquisition grace, then opens call-only ICE. Signed SDP conveys the mode; the answerer obeys it. Late shared leases are released without closing the network connection. Dedicated peer certificates are pinned for the accepted call. Cancellation prevents late creation, and cleanup closes only owned peers. Unit tests cover timeout and failure; live fault injection verified automatic fallback in both initiating directions. This is controlled failure testing on two phones at home, not a new remote-city/mobile-network field trial. No release built or installed.
