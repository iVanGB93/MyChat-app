Measured bottleneck
Instrumented cold wake: account inspection 41ms, native password derivation

Change and security boundary
The existing OS-protected remembered credential optionally contains a v1
salt-bound derived scrypt key. It stays in the same Expo SecureStore entry,
keychain service and accessibility policy as the previously saved password.
No derived key is stored in AsyncStorage, diagnostics, public identity records,
or on an AoN. Explicit password attempts still use the unchanged native KDF:
scrypt N=131072,r=8,p=1,32-byte output. Only policy-authorized remembered resume
can use the saved derived key. Account matching, device-secret HKDF binding,
vault AEAD and root/device/history validation are unchanged.

Legacy credentials upgrade after successful resume. Missing/malformed cached
fields or a changed vault salt use normal derivation. A structurally valid but
incorrect key fails vault authentication, clears the in-memory cache and does
not silently bypass it. Explicit valid password login can repair such a cache.
Manual/automatic locking still gates startup and removes the secure credential;
removal purges the same entry. Epoch checks prevent a racing resume from
unlocking or rewriting credentials after manual lock. Owned byte copies are
zeroed on clearing; this is not a claim of complete JavaScript memory erasure
or a formal security proof. OS-keystore compromise remains outside this boundary.

Notification processing now reads independent database/context and preference/
policy inputs concurrently; cancellation uses one displayed-notification
snapshot instead of two. Account/lock, mute/block, duplicate and read checks
remain. Diagnostic output contains durations only.
