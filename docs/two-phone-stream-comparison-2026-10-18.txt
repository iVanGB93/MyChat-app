Measurement contract
Normal queueRootAttachmentSource -> ordinary preparation, message descriptor,
attachment journal, authenticated peer connection, received-file publication,
final checksum, and signed delivery receipt. Not the old isolated stream lab.
Fixture: deterministic xorshift bytes, 1 MiB +19 or 10 MiB +19, matching across
modes. Fixture creation and its independent expected SHA256 occur BEFORE timing.
Timer: host performance.now before queue invocation until polling observes the
receiver's ordinary delivered state. Includes preparation, transfer, verification,
chat bookkeeping, CDP overhead, and up to approximately one polling interval.
Polling interval 250ms plus CDP evaluation latency. No cross-phone clock subtraction.
Receiver file size and native SHA256 are independently checked after this timer;
ordinary protocol verification is already inside it. Sender delivery confirmation
is then checked. The senderReceiptObservedMs diagnostic additionally includes this
external file audit and polling; it is NOT precise signed-receipt arrival latency.
Preparation is recorded from the actual sender timing stage, not enqueue return.
Stage milliseconds may overlap; do not sum them to reconstruct elapsed time.

Path control
The optimized stream requires authenticated RTC; raw LAN is not eligible.
Temporarily suppress only Dev LAN discovery using a reversible native-method
wrapper; the real application discovers and authenticates RTC through its usual
signaling. Both modes use that same RTC peer connection, not a desktop data relay.
The snapshot's route='internet' is a logical route label, not proof the file
traversed the public Internet. These are two phones at home, not a WAN benchmark.
For the chunk mode, a temporary __DEV__-guarded receiver hook returns 'unavailable'
only for the exact synthetic sender/checksum and a short expiry. All regular
chunk encryption, Merkle verification, authentication, final hash, publication,
and receipts remain enabled. Streaming uses the normal 16KiB binary frame /
256KiB window and native admission checks. No protocol parameter was changed.
Receiver stream-verified events confirm streaming; bypass counts and ordinary
read/write/network counters confirm chunk mode. No fallback was mislabeled stream.
Temporary hook and in-memory instrumentation are removed after the comparison.

Repetition and limitations

Work difference
10MiB chunk runs: 855 receiver attachment network calls, 854 file write calls,
111 checkpoints, 8,889-8,890 lease checks.
10MiB stream runs: 1 receiver attachment request, 5 worker checkpoints,
686-709 lease checks. Stream binary frames/ACKs and writer calls are NOT counted
by the ordinary request/writeFile timers; this is not a claim of only one
network packet, one write, or zero CPU work. Both modes prepared the regular
encrypted fallback attachment first. Preparation remains a future opportunity.
First 10MiB chunk run ended at thermal [1,0]; automatic cooldown reached [0,0]
before the next run. All other runs began and ended at [0,0]. This is a device
thermal observation, not proof of a specific power or CPU-energy reduction.

Conclusion
Normal-chat authenticated RTC streaming was substantially faster for these
larger files. Keep encryption, native admission, whole-file verification,
permission/cancellation checks, and signed receipts. Preserve compatible encrypted
chunk fallback. A direct raw-LAN route still does not automatically get this RTC
stream; do not extend plaintext streaming onto that route without an authenticated
encrypted transport design and verification. No such change was made here.
