Direct-first attachment preparation — 2026-10-23

Implemented locally, not committed/pushed/deployed

Attachment v4 retains whole-file WebRTC streaming and 3,000,000-byte encrypted
relay blocks. Direct traffic still requires authenticated recipient/device-bound
DTLS, file checksum verification, current job/policy checks and a signed receipt.
Normal chat envelope encryption is unchanged.

Changed contract
- Manifest root is now an independent per-file Ed25519 public verification key.
  Its random signing seed stays in sender-private app storage; it is NOT derived
  from the recipient's encryption key and is NOT included in chat descriptors.
- Manifest checksum is SHA-256 over a domain-separated serialization containing
  the random encryption key and plaintext checksum. This binds the file without
  exposing a public plaintext hash to custodians. The private descriptor retains
  the actual checksum and encryption key and must match that commitment.
- The sender signs this manifest before producing any relay ciphertext.
- On demand, XChaCha20-Poly1305 encrypts one 3 MB block (or the final tail). An
  Ed25519 signature binds its ciphertext hash, index/AAD, time bounds and content
  commitment. Custodians verify this before storing; receivers also verify AEAD
  and the complete file checksum. Shared grants reuse the content context but
  keep recipient-bound manifests and receipts.
- Retry caches preserve exact ciphertext/signatures. A lazy first relay pass
  verifies the source checksum and records local block hashes; later reads check
  only the requested plaintext block. Altered uncached source bytes fail closed.
- Public block-stream capability is now 4. Older blocks/manifests are rejected;
  no legacy attachment decoder was restored. Smaller DTLS/SCTP frames remain
  transport framing, not application-level encrypted file blocks.

Security qualification
This is a changed signed-manifest contract, not a byte-equivalent optimization
or a formal security proof. Existing peer authentication, DTLS, AEAD, signature,
private-storage and cryptographic-library assumptions remain. The attachment
signer may authorize ciphertext lazily; the receiver's signed checksum commitment
still fixes final content before delivery is acknowledged. Tests cover tampering,
wrong bindings/keys, source/cache corruption, cancellations, retries, receipts,
group grants, and independent Node/OpenSSL verification of block signatures.

Source boundaries

attachmentTransfer and groupCustodyMessages are copied from mobile to the

the matching capability bump on each side: its pre-existing mobile-only setup
timeout changes were NOT copied over or reverted. The AoN shared-source entry

Main Axonic-neuron worktree and unrelated staged/unstaged work were preserved.

Rollout boundary
No production build, phone installation, live AoN update, commit, push or reset.
This version changes the attachment format and requires coordinated rollout.
Do not install over populated v3 stores blindly: this work does not migrate or
delete old attachment rows. Validate/plan unsupported-history handling before
an official-app rollout; retained old files were not removed by this work.
