CALL FINDING AND CONFIRMED RINGING — OCTOBER 12, 2026

Problem: the outgoing coordinator immediately exposed ringing once an invitation was saved, so an offline peer appeared to ring and the caller heard ringback. Existing signed CallControlReceipt explicitly proves durable admission only, not notification presentation or media connection.

Outgoing views now begin in finding, displayed as Finding… without ringback. The existing signed call-control v1 ringing event (already supported by protocol verifiers) is used as a recipient presentation announcement. No signature encoding, wire version, encryption or caller/callee role rule changed. Durable ringingAcknowledged reconstructs verified journal state and requires an admitted ringing event that has not been superseded by that device's rejection/busy state. Receipts, relay storage and FCM submission alone cannot satisfy this check. Acceptance moves to Connecting immediately; selection acknowledgment still gates media. Finding expires with Peer unavailable, while confirmed unanswered ringing expires with No answer.

Foreground incoming-call UI confirms after mounting, with bounded one-second retries for transient account/runtime startup failure and idempotent durable submission. Background sync confirms only after allowed notification presentation succeeds, checks OS authorization/channel blocking, and never treats a failed display as proof. Confirmation is tied to the current incoming call, identity/device, invitation and valid journal state; cancellation or terminal state prevents later confirmation from reviving a call. Silence preferences still apply.

Compatibility: existing peers already parse the v1 ringing event, but older peers that never emit presentation announcements leave updated callers in Finding until an acceptance arrives. A locked/headless FCM handler has no unlocked identity signing key, so a displayed locked notification alone does not mint this confirmation. Ringing begins when an unlocked recipient runtime can confirm presentation. This deliberately avoids treating FCM acceptance as evidence that a person’s device rang.

Validation: full npm run check passed, including TypeScript, unit tests, cycles, module boundaries and consolidation. Added regressions for receipt-only silence, signed presentation, idempotent announcements, acceptance, unavailable timeout, unadmitted announcements, late cancellation, denied/blocked/failed notifications, silent Finding and transient foreground confirmation retries. Multi-device decline expectations now remain Finding while other devices have not confirmed ringing.
