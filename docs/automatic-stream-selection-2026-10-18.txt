Automatic authenticated stream selection — October 18, 2026

Scope and preserved contract
Mobile connection-selection and stream-admission scheduling only. No encryption
primitive, chunk size, file manifest, key derivation, signed signaling format,
native admission limits, final SHA256, or delivery-receipt format changed.
No AoN update, normal-app installation, production build, commit, push, message
deletion, queue flush, or data reset. Existing dirty work was preserved.

Prior behavior
Ordinary direct LAN could win permanently over RTC because the connection pool
ranked LAN above Internet routes. The optimized encrypted stream requires
authenticated RTC/DTLS; it is never allowed on the raw LAN socket.
The transfer worker already supports streaming after a verified chunk prefix
and selecting a newly connected sender instead of a custodian. Selection was
the missing link for a working LAN connection.

Implementation map
- persistentAxon.ts: optional attachmentStreams=1 hello capability, outside the
  bounded legacy features array. Only advertise with local guarded stream support
  and signaling. Expose the exact remote device only on a current authenticated
  session with mutually supported stream/signaling capabilities.
- composition/neuronRuntime.ts: advertise only with both Android native identity
  and stream guards present. Configured AoNs are not advertised as RTC-capable
  by inference from addresses or introductions.
- identityNetwork.ts: derive stream preference from the current peer session.
- neuronConnections.ts: negotiated RTC may promote LAN. Reuse existing bounded
  make-before-break authentication, retries, pool capacity, and cancellation.
  Do not let subsequent LAN advertisements downgrade a working eligible RTC
  connection. Preserve a separate wider-network route when making room at capacity.
- lanIdentityRuntime.ts: transfer demand may request RTC through signed signaling
  over the existing authenticated peer connection; deterministic lower-account
  dialing remains unchanged. At most five requested peers, 30-second leases,
  exact device checks, no configured-bootstrap promotion, clear on owner/lock/stop.
  Demand refresh does not reset connection backoff. Idle LAN discovery itself
  does not create stream-upgrade demand.
- rootAttachmentStreams.ts: request negotiation locally and through the existing
  direct-stream operation on the sender, so either dialing role can initiate.
  Return unavailable promptly while RTC negotiates; encrypted chunks keep moving.
  Recheck job/contact/account liveness before requesting. Report the verified
  chunk count present when a successful receive stream started, without IDs/content.

Late connection / safety qualification
If a sender connects after custody/chunk downloading began, the worker can
select it and attempt the authenticated stream on a later worker pass. This
does not bypass backoff, permissions, cancellation, expiry, or receiver-device
binding. Stream is not a resumable byte-offset protocol: it reads the full file
into an attempt-owned temporary file. Keep the existing verified prefix until
that complete stream passes its hash; failed/interrupted streams leave it usable.
This can resend some bytes after an upgrade. Nearly-complete transfers may finish
before negotiation; no claim that every late upgrade is optimal in every network.
No user-visible delivery is emitted before normal verification/publication and
signed receipt. Relay-stored encrypted chunks remain compatible.

Validation contract
Use the two existing com.axonic.dev accounts on SM-S948U1 phones, API 37.
Native Dev binary 1.1.22/93 unchanged in this task; Metro loads updated sources.
Synthetic deterministic 10 MiB +19-byte files, fixture creation/hash excluded.
Host monotonic queue invocation through observed receiver delivered status includes
preparation, network transfer, actual final verification, bookkeeping, and CDP/
250ms polling overhead. Independent native file SHA256 and sender signed-receipt
completion checked afterward. LAN discovery remains enabled; no stream bypass
or routing override is used for the automatic-upgrade runs.
These are functional device observations, not production throughput guarantees.

Fault-injection qualification
The first attempted failure test reused an already-open RTC connection, so it
did not exercise createOffer failure. Its file still passed integrity/receipt
checks in 5,488ms. The harness marked the test incomplete and rejected it as
fallback evidence; retained raw result and synthetic message:
  builds/two-phone-stream-comparison-1792304201555.json
384 messages on A and 139 on B afterward, all prior keys retained.
The corrected fault test restarts only Dev processes, rechecks identities and
all message keys, and refuses to send if RTC is already connected. It temporarily
rejects offers only on Dev peer connections with the identity channel label;
call channel offers are not targeted. Restore methods in finally and by timeout.

Conclusion / remaining limits
On-demand authenticated make-before-break promotion works on both physical Dev
phones with LAN enabled. Safe no-RTC fallback and subsequent mid-file recovery
also passed. The source byte-offset limitation remains; this work intentionally
does not introduce a new stream wire format, remove cryptographic checks, or add
RTC to AoNs. Official apps need a later approved release to receive these changes.
